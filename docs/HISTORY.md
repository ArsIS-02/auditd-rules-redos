# Как создавался свод правил

Этот документ — хронология настройки аудита на домашних хостах РЕД ОС: что было
на старте, какие ошибки встретились, как их диагностировали и к каким решениям
пришли. Большая часть проблем типична для любого RHEL-подобного дистрибутива,
поэтому описание может пригодиться и за пределами РЕД ОС.

Исходные условия:

- несколько хостов РЕД ОС на **aarch64** (в т.ч. Raspberry Pi) и на **x86_64**;
- `audit` 3.1.3;
- события уходят в **Graylog** и **Wazuh**;
- управление — по SSH с рабочей станции на Windows.

---

## 1. Отправная точка: большой «шумный» набор

На хостах стоял объёмный набор правил, собранный из разных публичных профилей:
около 130 правил в `auditctl -l`. Он работал, но отчёт по ключам выглядел так:

```
$ sudo aureport --summary --key | head
11025  network_socket_created
   65  susp_shell
   21  cron_persistence
   18  audit_tools
   ...
```

Одно правило давало на два порядка больше событий, чем все остальные вместе:
каждое создание сокета любым процессом — systemd, chronyd, агенты сбора логов,
DNS-запросы. В SIEM такие события только мешают искать настоящие инциденты.

**Решение** — записывать создание сокетов только в пользовательских сессиях:

```
-a always,exit -F arch=b64 -S socket -F a0=0x2 -F auid>=1000 -F auid!=-1 -F key=network_socket_created
-a always,exit -F arch=b64 -S socket -F a0=0xA -F auid>=1000 -F auid!=-1 -F key=network_socket_created
```

Два момента, которые легко упустить:

- **`auid`, а не `uid`.** `auid` (loginuid) — это идентификатор пользователя,
  который вошёл в систему; он не меняется после `sudo` и `su`. Поэтому
  администратор, выполнивший команду через `sudo`, по-прежнему попадает в журнал
  (в тесте ниже — `auid=1000 uid=0`). Фильтр по `uid` такие действия потерял бы.
- **`auid!=-1` обязателен.** У служб, запущенных не из пользовательского входа,
  loginuid не задан и равен `4294967295` (это `-1` как беззнаковое число).
  Это число больше 1000, и без второго условия фильтр `auid>=1000` пропустил бы
  весь тот же шум.

Тот же фильтр поставлен на изменение прав, удаление, переименование и создание
файлов.

## 2. aarch64: syscall, которых нет

Первая попытка загрузить общий набор на aarch64 оборвалась на ошибке
`Syscall name unknown: chmod`.

В ядре ARM64 (как и в других архитектурах на «новой» общей таблице системных
вызовов) нет устаревших вызовов `chmod`, `chown`, `lchown`, `open`, `creat`,
`rename`, `unlink`, `rmdir`, `mkdir`, `link`, `symlink`. glibc на этих
платформах реализует их через `fchmodat`, `fchownat`, `openat`, `unlinkat`,
`renameat`, `mkdirat`, `linkat`, `symlinkat`. Значит, и правила должны
ссылаться только на них.

Подтверждение из журнала после исправления:

```
type=SYSCALL ... arch=c00000b7 syscall=53 ... auid=1000 uid=0 ... comm="chmod" exe="/usr/bin/chmod" key="perm_modification"
```

`arch=c00000b7` — это AARCH64, `syscall=53` — `fchmodat`. Вторая запись в том же
выводе (`syscall=54`, `comm="sudo"`) — это `fchownat`: `sudo` меняет владельца
своего терминала `/dev/pts/N`. Это не ошибка правила, а честная фиксация.

Таблица соответствий — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 3. Частичная загрузка: auditctl останавливается на первой ошибке

После правки syscall число правил в ядре всё равно было меньше ожидаемого.
Причина — поведение `auditctl -R` (его вызывает `augenrules --load`): при первой
ошибке он **прекращает** обработку файла. Всё, что ниже битой строки, просто
не загружается, а уже загруженное остаётся.

Полезный приём для диагностики: каждое правило `-w` выводит предупреждение
`Old style watch rules are slower`. В наборе 45 правил `-w`, и по числу
предупреждений видно, докуда дошла загрузка:

| Предупреждений | Что это значит |
|---|---|
| 45 | все `-w` обработаны |
| 42, затем ошибка | остановка на правиле с `chmod` |
| 12 | загружено только начало файла (аудит + учётные записи) |

Надёжный критерий успеха — число правил в ядре равно числу строк `-a`/`-w`
в файле:

```bash
grep -cE '^-[aw] ' /etc/audit/rules.d/99-custom-aarch64.rules
sudo auditctl -l | wc -l
```

Именно эту сверку делает `deploy/deploy.sh`.

## 4. aureport показывает историю, а не текущие правила

Сразу после замены правил отчёт продолжал показывать тысячи событий
`network_socket_created`, а при повторных запусках число уменьшалось:
7780 → 7532 → 7480 → 7431.

`aureport` и `ausearch` анализируют **файлы журнала**, а не правила в ядре.
Ключ `-ts recent` означает «последние 10 минут», поэтому старые события
постепенно выходят за пределы окна — отсюда «падающие» цифры. Старые ключи
(`susp_shell`, `etcpasswd`, `software_mgmt`) в отчёте — тоже история.

Правильный замер:

```bash
sudo ausearch -k network_socket_created -ts recent 2>/dev/null | grep -c 'type=SYSCALL'
```

Так же с `lost` в `auditctl -s`: это накопительный счётчик с момента запуска
`auditd`, смотреть нужно на его рост.

Журналы при этом **не очищались**: `truncate` на `audit.log` уничтожает
доказательную базу, а для замеров достаточно временных окон.

## 5. Адаптация под конкретный хост: SELinux и UID служб

На одном из хостов aarch64 проверка окружения дала:

```
$ uname -m; auditctl -v; getenforce; id chronyd
aarch64
auditctl version 3.1.3
Disabled
id: «chronyd»: нет такого пользователя
```

Из набора были убраны:

- **правила с `-F subj_type=...`** (исключения для `crond_t` и `chronyd_t`):
  без работающего SELinux у процессов нет SELinux-типа, правило не загрузится;
- **исключение `-F uid=986`** для chronyd: UID был взят из чужого окружения,
  а самой службы на хосте нет;
- **исключение для `/dev/shm`** (`-a never,exit -S all -F dir=/dev/shm/`):
  оно отключало аудит любых операций в разделяемой памяти — ровно там, где
  работают некоторые техники вредоносного ПО.

Итог для aarch64 — **55 правил**, одинаковых для всех ARM-хостов.

Для x86_64, где SELinux включён, исключения по `crond_t` оставлены, а
`deploy.sh` сам вырезает их на хостах с `SELinux Disabled`.

## 6. Доставка файла на хосты: CRLF, права и буфер обмена

Самая длинная часть истории — не правила, а то, как довезти файл до хоста
целым.

**Windows → scp.** Файл, отредактированный в Windows и переданный через `scp`,
на одном из хостов дал:

```
parameter passed without an option given
There was an error in line 59 of /etc/audit/audit.rules
```

Строка 59 сгенерированного `audit.rules` — последняя строка набора, то есть
повреждён был конец файла. Точно установить причину не удалось (файл перезаписали
при исправлении), но такую ошибку дают и Windows-переводы строк (CRLF), и
обрезанная при копировании последняя строка. Решение на будущее —
`.gitattributes` с `eol=lf` в репозитории и проверка файла до загрузки.

Номер строки в сообщении относится к **сгенерированному**
`/etc/audit/audit.rules` (без комментариев, с заголовком), а не к вашему файлу
в `rules.d`: `sudo sed -n '59p' /etc/audit/audit.rules`.

**`sudo cat > файл`.** Под обычным пользователем команда

```bash
sudo cat << 'EOF' > /etc/audit/rules.d/99-custom-aarch64.rules
```

даёт `Отказано в доступе`: перенаправление `>` выполняет оболочка самого
пользователя, а не `sudo`. Правильно — `sudo tee файл > /dev/null << 'EOF'`.

**Вставка heredoc из буфера.** Блок на сотню строк, вставленный в SSH-терминал,
на двух хостах x86_64 «склеился»: следующая команда оказалась внутри файла,
а `EOF` — на одной строке с текстом правила, и heredoc не закрылся там, где
нужно. В результате получился обрезанный файл.

**Пустой rules.d и старый audit.rules.** Когда файл в `rules.d` не создался
(из-за двух проблем выше), `augenrules` загрузил то, что лежало в
`/etc/audit/audit.rules` с прошлых попыток: сотни строк старого профиля, ошибки
`Rule exists`, `Unknown user: ntp`, `No such file or directory`, и в ядре
оказалось больше сотни правил (на одном из хостов — 112) вместо ожидаемого набора.

Выводы, заложенные в `deploy/deploy.sh`:

1. файл берётся из git-клона, а не из буфера обмена;
2. до загрузки проверяются BOM, CRLF, строки, не начинающиеся с `-`,
   не-ASCII символы в правилах и «старые» syscall на aarch64;
3. все прежние `*.rules` из `rules.d` убираются в резервную копию — `augenrules`
   склеивает все файлы каталога;
4. после загрузки число правил сверяется с файлом, при расхождении —
   автоматический откат.

## 7. Результат

| | aarch64 | x86_64 |
|---|---|---|
| Правил | 56 | 61 (59 без SELinux) |
| Хостов | 4, загрузка подтверждена | синтаксис проверен, на хосте не подтверждён |

Проверка на рабочем хосте aarch64 после установки:

```
$ sudo auditctl -l | grep network_socket_created
-a always,exit -F arch=b64 -S socket -F a0=0x2 -F auid>=1000 -F auid!=-1 -F key=network_socket_created
-a always,exit -F arch=b64 -S socket -F a0=0xA -F auid>=1000 -F auid!=-1 -F key=network_socket_created

$ python3 -c "import socket; s=socket.socket(); s.close()"   # в сессии через sudo
$ sudo ausearch -k network_socket_created -ts recent | tail -1
type=SYSCALL ... arch=c00000b7 syscall=198 success=yes exit=3 a0=2 ... auid=1000 uid=0 ... comm="python3" exe="/usr/bin/python3.11" key="network_socket_created"
```

`syscall=198` — `socket` на aarch64, `a0=2` — `AF_INET`, `auid=1000` при
`uid=0` — действие пользователя через `sudo` зафиксировано.

## 8. Исключение для крона GLPI (версия 1.6)

Через два дня работы набора в Graylog обнаружился ровный поток записей с
ключом `unauthorized_access_attempt` — около 940 в сутки с одного хоста:

```
audit[...]: SYSCALL ... syscall=56 success=no exit=-13 ... uid=48 euid=48
            comm="php" exe="/usr/bin/php" key="unauthorized_access_attempt"
audit: PATH item=0 name="/etc/krb5.keytab" mode=0100600 ouid=0 ogid=0
audit: CWD cwd="/usr/share/httpd"
```

`exit=-13` — это `EACCES`: пользователь `apache` (uid 48) пробует открыть
keytab с правами `0600` и владельцем root. Источник нашёлся в журнале cron:

```
(apache) CMD (/usr/bin/php /usr/share/glpi/front/cron.php)
```

Штатное задание GLPI, раз в минуту. Отказ случался примерно на семи запусках
из десяти и всегда через 9 секунд после старта — то есть только тогда, когда
кроне доставалась сетевая задача.

**Что проверялось и не подтвердилось.** Сначала казалось, что дело в
Kerberos-аутентификации LDAP: в GLPI не оказалось ни одного LDAP-каталога.
Потом — в сборе почты через `php-imap`, где библиотека c-client пробует
Kerberos раньше пароля: почтовых серверов тоже не настроено. Наконец,
запуск крона с `KRB5_TRACE` оставил файл трассировки пустым, хотя сам файл
был создан, то есть переменная до задания дошла. Вывод: keytab открывает не
библиотека Kerberos через стандартный поиск, а что-то внутри PHP напрямую.
Точного виновника найти не удалось, и дальнейшие раскопки были признаны
несоразмерными: отказ безвреден, приложение работает.

**Что сделано.** Перед общим правилом по `/etc` добавлено исключение,
суженное до одного файла и одной программы:

```
-a never,exit -F arch=b64 -S openat -F path=/etc/krb5.keytab -F exe=/usr/bin/php -F success=0
```

Порядок обязателен: ядро применяет первое совпавшее правило, поэтому `never`
должно стоять выше `always`.

**Почему не по программе целиком.** Вариант `-F dir=/etc -F exe=/usr/bin/php`
загрузился бы так же, но перестал бы записывать любые неудачные открытия в
`/etc` со стороны PHP — это ровно та картина, которую даёт разведка через
веб-шелл. Слепая зона такого размера дороже, чем 940 записей в сутки.

**Почему `-F path=` безопасен.** Опасение было в том, что фильтр по
несуществующему файлу оборвёт загрузку (а в этих файлах одна ошибка
останавливает всё, что ниже). Проверка показала обратное:

```
$ sudo auditctl -a never,exit -F arch=b64 -S openat -F path=/etc/nonexistent-audit-test -F success=0; echo "rc=$?"
rc=0
```

`auditctl` принимает правило с путём к отсутствующему файлу, так что на
хостах без keytab набор загрузится полностью.

## Что можно улучшить

- Перевести `-w` на синтаксис `-a always,exit -F path=... -F perm=...` —
  уйдут предупреждения `Old style watch rules are slower`.
- Добавить `fchmodat2` и `openat2` (ядро 6.6+ и 5.6+). Пока не добавлены:
  если версия `auditctl` не знает имя syscall, загрузка оборвётся на этой строке.
- Добавить `-e 2` (неизменяемые правила до перезагрузки), когда набор
  окончательно устоится.
- Подтвердить набор x86_64 на живом хосте и зафиксировать число правил.
